## 3 Qwen与LLaVA采用LoRA监督微调

两者统一采用Transformers 4.57.1 + PEFT 0.17.1的LoRA SFT，沿用现有基础评测的固定模型revision、processor和原生聊天模板。建议克隆原评测Conda环境再加PEFT。入口scripts/train_lora.py，配置configs/training/下两个JSON；现有300/60数据直接复用，GPU训练待服务器验证。

| 项目 | 建议起点 性能待验证 |
|---|---|
| 权重与图像处理 | 沿用各自固定revision、processor和当前图像分辨率设置 |
| 可训练部分 | 仅语言解码器注意力投影的LoRA；冻结视觉编码器和多模态投影器 |
| 模块选择 | 根据实际named_modules限定语言分支，不能只用通用q_proj后缀误选视觉层 |
| LoRA | r=16，alpha=32，dropout=0.05 |
| 优化 | 初始学习率5e-5，AdamW，warmup_ratio=0.1 |
| 批量 | 每卡1条，梯度累计8步，开启梯度检查点 |
| 训练预算 | 最多3个epoch；当前配置按独立验证集eval_loss最低选checkpoint；生成式Macro-F1选优尚未实现 |
| 数值精度 | A800上两者训练BF16、LoRA参数FP32；推理仍为Qwen BF16、LLaVA FP16，训练精度独立记录 |
| 监督目标 | 图片+配文+baseline任务提示 → 来源一致性派生标签；loss仅计算assistant答案及结束token |
| 保存 | 每个模型单独保存adapter、配置、分割ID、训练命令、环境、loss和验证指标 |

这些数值是待试起点，不是已选定的最优参数。先对少量训练数据验证前向、反向、非空答案监督、可训练参数和显存；不得根据当前70条评测分数挑训练轮次。

多模态collator用同一图片分别处理用户前缀和完整对话，强制核对token前缀一致、答案解码等于目标标签，将用户/图像/padding设为-100，只监督答案及结束token。CPU张量测试已通过，真实模型仍需两步检查；不能把整段输入重构loss下降当成分类能力提升。

max_length4096只作为检查上限，超长直接报错，不静默截断。完整训练前逐条做token/mask检查，避免训练中途才发现超长样本；运行前重新确认GPU2资源。

现有HF推理入口已接入PEFT适配器加载，训练结束生成evaluation-config.json，核对基础模型/处理器身份并记录适配器内容指纹。smoke适配器拒绝进入正式评测。指南提供每模型一个nohup任务：训练成功后自动完整评测70条；已有基础模型和预测文件不覆盖。实现尚未在A800上运行，不保证提升。

## 4 DeepSeek与Kimi的提示词路线

### 为什么旧evidence可能没有改善

代码检查发现，evidence沿用了baseline定义，主要增加“检查态度、核对图文”等抽象步骤，并没有增加有标签的新信息。另外，它写明“没有正负主导就使用neutral”，而项目标注规范不希望把难以裁决的混合情感直接视为neutral。两者的边界需要统一。

这些是文本层面可核对的差异与潜在问题，尚不能证明旧prompt效果差的因果原因。已有单标签输出也无法证明模型执行了或没执行这些内部检查。

### 首选候选 类别边界加平衡多模态few-shot

推荐把“最值得优先试”与“已经最有效”分开。当前优先级如下：

| 候选 | 具体变化 | 优先级与理由 |
|---|---|---|
| P0 baseline | 原提示，不变 | 对照，重用或核验原基线 |
| P1 boundary_v1 | 简短明确主要评价对象、客观描述与态度表达、中性与混合评价的边界 | 先测成本低的单一变量，文件已准备但未测 |
| P2 boundary加6-shot | P1基础上增加6个独立人工复核的图文示例，每类2个，突出相邻类别差异 | 最优先的主优化候选，给出具体决策边界而非仅要求多思考 |
| P3 检索式few-shot | 对每个目标从独立示例库检索相关且互补的3或6个图文样本 | P2有收益且库足够大后再做；避免一次引入过多变化 |

few-shot并不必然提升；已有研究显示示例选择、格式和排列顺序都可能明显影响结果[3]，因此先在独立验证集比较P0/P1/P2，而不是在70条回归集上不断改到涨分。

P2的示例需覆盖可解释的对照：客观介绍与赞许、坏天气的事实与明确抱怨、漂亮照片与当前事件的不满。示例必须同时发送真实图片、配文与正确标签；不能只加图片路径字符串，或只给文本示例却称为多模态few-shot。示例可来自新训练数据；每个标签2例、顺序固定，必要时仅增加一次预先规定的顺序稳健性检查。不从本轮待评分的70条中挑错题及答案粘进prompt。

当前API实现一次请求只构建目标的一张图片和一个用户消息；P2/P3需要扩展消息构建，记录示例ID、图片哈希、标签来源和顺序，防止目标样本进入示例库。尚未实现，不把一份新增txt文件声称为完成了真正多图few-shot。

### 不优先的方法

- 单纯再加角色设定或更多“认真分析”句子：与旧evidence差异有限。
- 无反馈自我反思：不预设第二次回答一定更好；相关研究在推理任务中观察到自纠可能失败或退化[4]，不能直接外推为本任务必然无效，但缺乏优先投入依据。
- 多次采样投票：可能增加调用成本，系统性类别偏差也可能被重复，不作为第一步。
- 上下文校准：需明确如何获取可比较的类别分数或概率；当前接口只解析标签，不声称实现了概率校准。

### 选择方式与记录

1. 先审计API模型的基线、那1条无效输出及图像实际传输格式。
2. 在独立验证集上比较最多3个预先写定的候选：P0、P1、P2。两个API模型可分别选最佳候选，按Macro-F1优先、Accuracy辅助，不能只挑有利指标。
3. 固定prompt及示例后，在相同70条上各运行一次；保留负结果，并输出corrected/new_error/both_correct/both_wrong逐题对照。
4. 固定模型ID和路由、任务输入、输出预算、可支持的思考/采样参数、重试规则。若改输出预算或格式处理，应单列工程修复，避免把它全部计作语义提示的收益。
5. API组仍只输出一个标签，保留原始响应、returned_model和usage；成本与无效率也报告。未知平台单价不推算金额。
